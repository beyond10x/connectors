# Service and family compatibility

**Status: proposed specification; no new runtime codec or route is implemented.** This is the compatibility owner for `story:contracts-wire-compatibility` (E02), reviewed against `3ba2d29`. It supersedes local “optional/additive/no wire change” and version/projection defaults in the family documents. [Configured service v1alpha1](v1alpha1/semantics.md) records the existing implementation; [governed service v1alpha2](v1alpha2/semantics.md) supplies the proposed admission semantics subject to this binding. Individual stories still own family behavior. A compatibility disposition is not implementation support.

## 1. Independent version axes

| Axis | Rule |
|---|---|
| Semantic family and profile | `operations/v1alpha1` may gain a proposed `mutation` profile without becoming `operations/v2`. Each selected profile retains its stated meaning; a changed meaning needs an explicit new profile/version and refusal by readers that do not support it. |
| Service envelope | The implemented closed `v1alpha1` envelope cannot accept new members or enum values, even optional ones. The proposed extended envelope is named `v1alpha2` here. This selects the local specification's binding identifier, not a release or rollout. |
| Adapter authoring kind | `connectors.adapter/v1` and `/v2` are Connectors compiler input formats. Neither implies a service-wire version. No kind/schema is renamed or modified by this decision; future strict-reader extensions need their own compatibility decision and vectors. |
| Configuration and generated artifacts | Receiver configuration, bundle/index formats and generated manifests have their own readers/digests. A service-wire bump does not authorize a new field there. Reject unknown keys/formats; regenerate through their owning compiler. |
| Stream/control/data binding | A unary service envelope does not encode WebSocket control, media frames, callback proofs or secret entry. Each needs an explicitly selected, versioned binding with complete framing and limits. |
| CLI/product labels and historical protocols | Repository “v2”, a CLI migration name and old `v0alpha*` operation protocols are not any of the versions above. A client binary may implement several codecs; it selects exactly one per interaction, without fallback or resend. |

Adding a new operation-local schema under the existing `input`/`result` JSON slots is representable without extending the envelope. It does not make the new profile understood by an old typed consumer. Such a profile must be explicitly supported by the caller and every selected hop; existing closed payload types (`Page`, `QueryResult`, observations) do not accept arbitrary new fields merely because their outer envelope uses JSON.

## 2. Deterministic binding selection

The proposed extended binding uses **`GET /v1alpha2/describe` and `POST /v1alpha2/invoke`**, with envelope/descriptor `version: "v1alpha2"`. Existing **`/v1/describe` and `/v1/invoke` remain the legacy v1alpha1 binding**. Path selection resolves describe's missing request-version problem. A configured endpoint plus this fixed path identifies the binding; a discovery observation cannot switch the endpoint, credential, version or profile. No query/header/body override chooses a different codec on that path.

A client chooses its codec before describe. On the extended route, successful describe returns the common §5 Response with `request_id: null`, `status: success` and `result` containing the complete Descriptor; both version fields must equal `v1alpha2`. Describe failures use the same Response with `status: error` and no result. The legacy describe route retains its bare Descriptor success shape. The client checks the selected envelope and descriptor versions, exact schemas, instance/revision and required contract/profile support, then invokes that same binding. No client correlation id is invented for GET describe. `/healthz` establishes no version, profile, provider or admission support. Unknown/missing routes or incompatible descriptors stop selection; the client does not try a second route/version/credential or resend the request. A raw HTTP 404 or malformed response is not renamed into proof that a particular version is unsupported. An explicit operator reconfiguration is a new interaction.

A future v1alpha2 service exposes a legacy path only through the explicit projection in §3. With projection disabled, it may provide the legacy path's **bare v1 Error** with code `unsupported`, without provider dispatch; this small refusal endpoint advertises no legacy operations. Unrecognized paths may return ordinary HTTP route failures. Neither behavior describes today's old binaries as capable of negotiating the new codec.

On each invoke route, the selected codec strictly decodes the bounded envelope, then checks that its `version` equals the route's version before any policy-dependent business dispatch. Unknown/duplicate fields are refused; a decoded wrong version gives `unsupported`. Early errors on the proposed route use §5's explicit pre-envelope form. On the implemented legacy route, preserve the actual distinctions below.

| Bytes presented to current v1alpha1 implementation/reader | Actual baseline result |
|---|---|
| Unchanged descriptor, invocation, success or error | Accepted subject to existing auth/revision/input checks. |
| Descriptor in old shape, `version: v99` | Current client decodes the shape, then reports `unsupported`. |
| Descriptor with new root or operation member | Current client reports `upstream_protocol` before its version comparison. |
| Invocation in old shape, `version: v99` | Host returns correlated **v1alpha1 Response**, `error.code: unsupported`, zero adapter calls. |
| Invocation with `connection`, `approval`, `executor` or another unknown member | Host returns **bare Error**, `invalid_input`, before dispatch, even if a different version is also supplied. |
| Missing/invalid service credential or malformed/oversized request | Existing admission/framing failure may be a bare Error rather than a correlated Response. |
| Success/error response with a new member, or nested unknown error code/member | Strict response/error decoding refuses it. The current client's fallback can report an HTTP-derived error or `upstream_protocol`; it does not generally translate `invalid_input` to `unsupported`. |
| Shape-compatible response with wrong version or request ID | Current client reports `upstream_protocol` for correlation/version mismatch. |

Source: [core](../../crates/connectors-core/src/lib.rs), [server](../../crates/connectors-host/src/server.rs), [client](../../crates/connectors-client/src/lib.rs). Decoding failure is not evidence about a provider effect. A new mutation client that has sent an invocation and lacks a valid definitive response reports outcome uncertainty and never retries automatically, even if an HTTP failure resembles a version problem.

## 3. Legacy projection and federation intersection

Projection is **off by default**, permitted only for an explicitly configured `static-bearer` read surface whose complete semantics are unchanged. The receiver maintains an explicit eligible operation set. Eligibility requires the original input/output schemas, implicit configured connection, auth behavior, error vocabulary, no-retry policy, limits, cursor/provenance meaning and result visibility to remain valid. An absent `external_write` flag alone is not proof: exclude every mutation, managed/governed operation, effectful process/local-system/send/session operation and every profile requiring unavailable metadata or behavior. New generation-validation or refresh/retry requirements cannot be silently imposed while calling this the unchanged configured profile.

The legacy descriptor uses only the six original Operation fields and the original Descriptor/Error/Response shapes. It has its **own projection revision**, bound to the exact visible operation set, schemas, eligible binding/configuration and selected wire profile. The legacy invoke path resolves only against that set and revision. A guessed hidden operation is `not_found` before dispatch; a full/new descriptor revision is not a valid legacy revision. Do not accept a mutation through a hidden name, alternate connection, omitted approval or direct handler lookup. Projection strips new metadata only after proving its absence loses no required meaning; otherwise the operation is unavailable on that binding.

Each gateway route explicitly selects the downstream codec and supported profile intersection. A v1alpha1 leaf cannot perform governed or keyed mutation dispatch on the strength of a broad static credential. No gateway translates unknown outcomes into generic read errors, silently strips approval/context, or retries on a lost answer. The current one-hop read federation remains as documented. The [F03 one-hop proposal](delegation.md) now selects canonical preparation/approval subjects, receiver/request binding, proof types and nonce versus leaf-only redemption ownership. It remains unadvertisable until its actual binding and conformance exist; the withdrawn HMAC sketch is not a substitute.

## 4. Extended descriptor and invocation surface

These are closed objects. The original required fields remain; added fields are admitted only by the proposed codec. Optionality here controls emission by **new** readers/writers, never compatibility with an old reader.

| Object | Added field and exact disposition |
|---|---|
| Descriptor | `admission: {profile, audience?}` is required; `profile` selects static-bearer / identity-audience / delegated, and `audience` is present only for identity-audience. Profile support is advertised only after its binding exists. |
| Descriptor | `auth_profiles?` is a safe array of `{id, purpose, subject, scheme, flow, capabilities, evidence}`. All values come from auth.profile/auth.capability/auth.evidence vocabularies. Do not publish provider token/authorize/revocation URLs, registration secrets, credential references or the entire authored profile. |
| Descriptor | `connections?` is a boolean capability flag, true only when the managed connection surface is implemented and selected. The safe management operations still require their own schemas and admission. |
| Descriptor | `provides?` is an array of `{contract, profile, targets?}`; `targets` is a finite adapter-name array only for mediated-route capability advertising. This metadata does not expose a `forward` operation. |
| Operation | `effects`, `semantic_effects`, `risk`, `idempotency`, `approval` are required in the extended binding, including reads; their value shapes come from operations §3. Unsupported combinations are rejected before advertisement. |
| Operation | `requires_auth?` is **one alternatives array** of `{profile, scopes}` with `scopes` an array of strings. Its absence means no public auth-profile selector is provided by the configured binding, not anonymous access. Anonymous/parent-auth behavior still requires its explicitly selected profile. |
| Operation | `realization?` is `generic` or `implemented` when catalog curation is provided. `unresolved` belongs in catalog inventory only and is never callable. |
| Operation | `limits` is required: `{request_bytes, result_bytes, execution_ms, provider_ms, connect_ms}` positive integer ceilings; §7 defines first profiles. These are receiver declarations, not caller overrides. |
| Operation | `profile` remains **singular**. Generic read uses `generic-http`; generic mutation uses `mutation` with `realization: generic`; generic page uses datasource.records + `generic-http-page`. Catalog inventory also uses the selected singular profile. `profiles[]` is not a second runtime field. |
| Invocation | `connection?` is a nonempty safe managed connection string, never explicit null. It is omitted only when the selected business profile resolves one implicitly, or the selected host-management profile is explicitly instance/acquisition-scoped and rejects a selector. Describe/revoke/repair management requires the exact string. It never supplies credentials or a destination. |
| Invocation | `idempotency_key?` and `approval?: {reference, evidence}` follow mutation admission and replay rules. Neither can be smuggled inside business input as envelope authority. |
| Invocation | `executor?` is an assertion with `{agent, revision, authority_snapshot:{id,sha256}}`; validation compares it to trusted credential/configuration/grant bindings. It cannot overwrite tenant, principal, realm or authority. |

Static bearer authenticates **one receiver-configured service principal**, not individual humans sharing its bytes. Its stable principal and configured local tenant/realm absence are independent of credential rotation. An explicit configured local policy supplies its permitted operations/connections; an unavailable governed policy never falls back to it. Governed authentication first establishes tenant/principal/optional realm/current authority and any credential-verified executor. After strict decode, policy verifies any supplied executor assertion and constructs the admitted invocation context. An absent credential executor does not make a body assertion trusted; policy must establish that binding or refuse it. Where an executor was credential-verified, the assertion must match exactly.

## 5. Extended responses, audit and mutation observation

Successful describe is audited under the selected admission policy just like other admitted reads; explicit unaudited static reads alone use `not_required`. Every extended application response has `version`, nullable `request_id`, `status` (`success`/`error`), exactly one of `result`/`error`, `audit_ref` (nullable opaque string), `audit_status` and optional `source_audit`. A decoded valid invoke request echoes its request ID. GET describe has no request envelope and always uses `request_id: null`, including success. Before a valid bounded invoke envelope exists, `request_id` is null; never invent a correlation or copy malformed input into it. `source_audit`, when present after a verified downstream response, is `{instance, audit_ref, audit_status}` identifying the selected origin; it does not replace the gateway's own audit fields. Omit it when no trustworthy leaf audit observation exists.

`audit_status` is `complete` (durable final observation), `incomplete` (durable admission/anchor exists but final observation is unconfirmed), `unavailable` (no acknowledged durable record, ref null), or `not_required` (explicit unaudited static read profile, ref null). `complete` and `incomplete` require a non-null acknowledged reference; `unavailable` and `not_required` require null. Apply the same reference/status consistency to `source_audit`. References identify only acknowledged records. “Complete” describes the audit observation, not certainty about the business effect: an unknown business outcome can have a complete audit record. Record absence is never replaced by a plausible opaque string.

For audited operations, append/acknowledge an admission record **before dispatch** for reads as well as mutations; append the final observation separately, linked to that admission. For refusals before valid authentication/decoding, record the known stage and leave unverified tenant/principal/operation/input coordinates absent. Caller data never fills trusted audit coordinates. No single append-only row is claimed to contain a future result before dispatch. Audit storage ownership, retention and the atomic relationship with the attempt ledger are binding obligations, not a new storage engine specified here.

An unacknowledged admission audit prevents dispatch and gives safe `unavailable` with `audit_status: unavailable`, `audit_ref: null` (or transport failure if no reply can be sent). This is the explicit exception to the former impossible “every refusal has a durable ref” promise. After dispatch, final-audit failure gives `incomplete` and preserves whatever business outcome is actually known; it cannot turn an applied mutation into `not_attempted`, or claim a performed read never ran. The durable anchor remains correlatable for later audit recovery. Lost/ambiguous acknowledgement is not proof of no record, and must not cause redispatch.

After current operation/result admission, a mutation observation is encoded under **`mutation`**:

```json
{
  "classification": "applied",
  "attempt": { "instance": "selected-origin", "id": "00000000-0000-4000-8000-000000000001" },
  "original_request_id": "original-request",
  "replayed": false,
  "cause": null
}
```

All five fields are required when `mutation` is present. `classification` is the settled `not_attempted | refused | applied | unknown`. `attempt` and `original_request_id` are both null until an original attempt identity is safely known and disclosable, otherwise both identify the **same original** attempt/request; the outer request ID still correlates this delivery. `replayed` is a boolean, never a classification: true means returning an existing durable outcome under current replay admission. `replayed: true` requires both original identity fields; it cannot name an undisclosed or hypothetical original. An unresolved waiter may have original correlation with `replayed: false`. `cause` is null or `{code, stage}`: `code` is a base error code and `stage` is preflight / attempt_store / approval / dispatch / response / observation / audit. It carries a secondary safe cause such as timeout or failed outcome persistence, without provider messages or private ledger identifiers.

Denied current caller/result admission returns a safe ordinary error **without `mutation`**; it says nothing about a possibly existing original effect, record or key. Absence of mutation metadata is never interpreted as `not_attempted`. After admitting the observation, a preflight/prepare refusal can report `not_attempted` with null attempt identity; an uncertain lookup may report `unknown` with null identity. Do not invent an original attempt ref to make the schema look complete.

| Observed business fact | `status` / `error.code` | Mutation fields |
|---|---|---|
| Definitive success, result deliverable | success / no error | applied; original attempt identity; optional secondary persistence/audit cause |
| Definitive effect applied, result cannot safely be delivered | error / safe delivery failure such as capacity or upstream_protocol | **applied**, never changed to unknown merely to fit an error shape |
| Definitive provider refusal proves no business effect | error / original safe refusal code | refused; optional secondary persistence cause preserves the original refusal |
| This admitted new attempt definitely did not cross dispatch gate | error / specific safe cause, such as unavailable or approval_refused | not_attempted; no claim that an approval remains unspent |
| Relevant attempt may have dispatched; no definitive observation | error / **outcome_unknown** | unknown; optional cause `{code: timeout, stage: observation}`; missing response is treated conservatively by the caller |
| Exact admitted replay of Completed/Failed/Aborted/Indeterminate | preserve original status/result/code and classification | replayed true; original attempt/request identity; no new spend or dispatch; current delivery audit is separate |
| Pending duplicate waiter expires | error / outcome_unknown unless an authorized definitive original observation exists | unknown with original correlation when known; replayed false; no mutation of the original lifecycle |

Known provider success/refusal remains known even when terminal-store/audit writes fail. Conversely HTTP success or an ordinary provider 5xx does not establish effect certainty. New readers validate these combinations. Success with mutation metadata requires `applied`; refused/not_attempted/unknown require error. `classification: replayed`, success+unknown, or unknown without `outcome_unknown` is a protocol violation. A protocol violation after possible dispatch supplies no retry authority.

The new **closed error-code set** is the 13 existing codes plus: `approval_required`, `approval_refused`, `approval_replayed`, `idempotency_conflict`, `outcome_unknown`, `not_granted`, `stale_authority`, `connection_not_ready`, `route_unavailable`, `route_refused`, `insufficient_scope`, `session_not_ready`, `session_lost`, `offer_expired`, `offer_rejected`, `lease_expired`, `revoked`. A profile may emit only its declared subset. Payload state/reason enums (acquisition failures, connection state, evidence results, media terminal reasons, private refresh outcomes) are **not** additional ErrorCode members. Future additions require a new explicit reader contract, not an untyped error string. Error remains `{code,message,retry_after_seconds?}` with a safe message of at most 512 UTF-8 bytes; metadata is never hidden in message text.

HTTP success uses 200 and `status: success`. An application error uses `status: error` and the following exact HTTP mapping on the extended routes (including GET refusal and pre-envelope invoke refusal):

| HTTP status | Error codes |
|---|---|
| 400 | invalid_input, unsupported |
| 401 | unauthorized |
| 403 | forbidden, approval_required, approval_refused, not_granted, route_refused, insufficient_scope |
| 404 | not_found |
| 409 | stale_description, stale_cursor, approval_replayed, idempotency_conflict, stale_authority, connection_not_ready, session_not_ready, offer_rejected |
| 410 | session_lost, offer_expired, lease_expired, revoked |
| 413 | capacity |
| 429 | rate_limited |
| 500 | internal |
| 502 | upstream_protocol, outcome_unknown |
| 503 | unavailable, route_unavailable |
| 504 | timeout |

The selected client validates the closed envelope and this consistency mapping. Neither an HTTP error nor a mismatch proves non-dispatch: a mutation with no valid definitive observation remains uncertain and is never automatically retried. An error with known `mutation.classification: applied` retains that knowledge regardless of HTTP status. Ordinary unrecognized-route or transport failures outside this application binding need not manufacture an envelope. Legacy HTTP mapping is unchanged.

The auth families share the [host management boundary](../auth/management.md). Safe management may use selected extended operation payloads while the coordinator owns dispatch; protected completion and continuation delivery remain separately bound. Instance-scoped create/list never fabricate a selected business connection. The connection status vocabulary is the ordered seven-state viability reduction, with separate observation/validity times and nullable identity before activation; insufficient_scope remains an operation/acquisition refusal. The authored evidence_requirements value separates baseline from operation checks and needs its own supporting strict profile reader; it is not added to the public Descriptor.auth_profiles projection or current adapter schema.

The selected auth vocabulary now distinguishes direct `anonymous/none/http-anonymous` from child `mediated_access/parent/mediated-http` (purpose/scheme/capability; subject none for both). Safe auth-profile metadata reflects that distinction; a reader must explicitly support these enum values. Neither mode fabricates a child credential generation or provider identity: external_identity remains required-null when ready. The complete authored/configuration representation needs its own strict reader; the current host's required credential field has not become optional/null. static_config is deployment activation/materialization with no acquisition id/action; coordinator begin/status is unavailable for that path. Acquisition §4.0 owns required/forbidden OAuth fields and reserved-flow refusal. Generic service-wire selection grants none of these behaviors.

The proposed multi-target authorization-coverage payload in [evidence §4.4](../auth/evidence/v1alpha1/semantics.md#44-exact-authorization-targets-and-fan-out-budget-f08) adds the closed `authorization {complete,targets[{target{verb,api_group,api_version,resource,namespace,name,subresource},result}]}` field to the selected read payload. Its result enum is allowed/denied, never unchecked-as-denied; root complete must also be false for any denied target. It is not an added field accepted by today's strict Page. Only an explicitly supporting profile/reader may expose partial denied-target results; budget/unknown-permission failure uses unavailable, target overflow invalid_input, all denied forbidden. Private query capabilities and cache keys stay private. Incomplete partitions establish no discovery withdrawal; an independently complete comparable partition may prove absence in its own exact scope even when another partition makes the whole view partial. Permission coverage alone proves no provider exhaustion. Explicit all-namespaces Service selection uses its own exact F08 tuple and the same scan ceilings; it is not inferred from an empty namespace field.

The selected resource-discovery view additionally carries scope_ref/selection_revision, provider coverage partitions (complete/capped/denied/unavailable/not_scanned), retained-history truncation, and per-row observed/stale/withdrawn evidence with last positive generation/deadline. Exact field and null/omission rules are owned by resource discovery; current Page accepts none implicitly. Permission authorization coverage remains a separate F08 payload field. Mediated composition is one process with injected private ports; same-target route revalidation is a separately admitted host configuration/validation binding, not a new generic invoke operation or a service-wire provider proxy.

Deferred `execution`, `events`, resource management and live configuration families gain **no binding** through this matrix. A supported payload profile may use legacy framing only when its complete advertised semantics, error set, auth and limits satisfy §3; no new envelope member may appear there. Families needing extended metadata/errors use v1alpha2; their old-reader behavior is refusal, not information-dropping coercion.

## 7. Limits and compatibility obligations

For the proposed extended binding, ordinary configured/read and non-generic mutation operation ceilings are the existing 64 KiB request / 4 MiB result, 20 s execution / 15 s provider / 5 s connect. Every operation with **`realization: generic`** (generic-http reads, mutation writes, and generic-http-page reads) deliberately selects **256 KiB request / 4 MiB result, 40 s execution / 30 s provider / 5 s connect** to accommodate its authored 30 s provider budget without placing it behind a 20 s service cutoff. This is a new profile requirement, not a claim that the current host accepts larger requests or longer work. A receiver unable to supply the declared limits refuses the profile; it cannot silently clip it and advertise conformance.

Request/result byte ceilings include the service envelope; the binding reserves space for bounded metadata/error replies and refuses an oversized object explicitly. The host enforces a bounded aggregate framing ceiling before the operation is known, then that operation's declared lower ceiling before dispatch. Policy, admitted preflight, audit and provider work share the operation execution budget; they do not each receive a fresh deadline. Connect is inside provider time. The gateway's end-to-end budget must accommodate its selected downstream profile; no hop can silently reset it. A separate conformance binding must cover deadline/cancellation and outcome knowledge, rather than assuming these advertised numbers execute themselves.

The `approval-subject` helper is a distinct selected profile: 272 KiB request / 64 KiB result / 20 s total / 15 s downstream-control / 5 s connect. Its provider_ms ceiling is unused for provider I/O, which the helper forbids; the profile explicitly applies that field to downstream control. It is neither an ordinary nor generic execution limit. Signed one-hop requests additionally require the bounded Authorization proof and Connector-Dispatch-Id response correlation specified by delegation.md; no new public Response member is added.

The following remain implementation obligations: separate strict codecs/routes; old-byte vectors; exact profile support/projection/invoke checks; schemas for all selected public payloads; safe error and observation combination validation; receiver-owned auth configuration; audit failure framing; and complete selected stream/callback/delegation codecs. Proposed context verification, audit/attempt atomicity and the selected F03 delegation protocol are not implemented by ESS value types.

The [verification record](../../docs/evidence/wire-compatibility-20260908/verification.md) records old-reader evidence, selected outcome vectors, matrix coverage and independent rechecks. It must distinguish declaration/schema checking from executing a service or sequential ESS trace. Runtime implementation and external publication remain outside this story.
