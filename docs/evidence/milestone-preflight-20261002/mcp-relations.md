# MCP relation preflight — accepted facts versus decisions

**None of the eight complete `UNMAPPED` relations can be assigned a cardinality and lifecycle solely from the already accepted contracts.** This is explicit, not an absence inferred from thin documentation: outbound `client/v1alpha1/semantics.md:721–727` reserves five relations, and inbound `server/v1alpha1/semantics.md:122–130` preserves the caller marker and the separate absent session→Connection relation. Single-owner admission is already selected; a durable `McpCaller` entity is not.

This does **not** mean eight new operator questions. Five are binding/storage/lifecycle design choices to record and review before implementing their selected mapping. One concerns the caller model and belongs with the existing caller decision if a multi-caller placement is selected. The final two are the explicitly filed operator decisions. The local single-owner slice can avoid introducing the caller model; outbound HTTP avoids the outbound process decision.

Paths below are repository-relative. Line citations identify the audited checkout; future normative documents should cite headings/phrases in living files, as the MCP contracts require. This audit read the preflight, all seven draft follow-ups, the two landed directional contracts, selection, native ESS, shared ownership models, census checks and both decision blockers. No validation, build, provider call or source/store mutation was performed.

## Eight relations: exact disposition

| Census edge | Facts already established | Proposed cardinality/lifecycle disposition now | What must be selected before resolving it |
|---|---|---|---|
| `McpServerBinding → ServiceConfiguration` | Explicit selection names one endpoint, transport and revision. The contract expressly declines whether the record is a `ServiceConfiguration`, `Connection`, or neither (`adapters/mcp/contracts/client/v1alpha1/semantics.md:123–150`). | **Keep UNMAPPED.** One endpoint does not prove one configured instance, nor ownership or delete behavior. | Binding identity relative to adapter instance/configuration; configuration revision changes; disable/removal/reselection effects. This is a new mapping decision, not the outbound-process question. |
| `McpServerBinding → Connection` | Shared Connection already names one configured instance, but the MCP binding has not been equated with that record (`ess/domains/auth_bindings.yaml:115–121`; client semantics:148–150). | **Keep UNMAPPED.** Do not add `connection_ref`, make binding identity equal to a Connection ID, or infer one/many from the shared Connection's own outgoing edges. | Whether one selected remote-server binding can have several saved identities/profiles, which record survives repair/revocation, and whether binding removal affects its Connections. Resolve jointly with configuration and custody. |
| `McpServerBinding → McpCapabilitySnapshot` | A discovery response is already a value with optional freshness hints. Discovery changes no binding field and acquires no credential (`adapters/mcp/spec/ess/domains/state.yaml:180–195`; client semantics:112–121). | **Keep UNMAPPED.** Continue to use a response value for contract examples; no durable relation, reverse binding carrier, cache entity or ownership cascade follows. | Whether to retain snapshots, their identity/key and credential/configuration partition, allowed count, invalidation and restart lifetime. Neither `ttlMs` nor one response proves persistence or a one-snapshot-per-binding relation. |
| `McpOutboundSession → McpServerBinding` | The interoperability revision may have a wire session; the primary revision is stateless. A lost legacy session is not replayed; a new request may establish a fresh session (`client semantics:582–613`). | **Keep UNMAPPED.** One live client/server pairing is not a durable binding/session cardinality. Do not create a session for every modern HTTP request. | Session persistence across owner/CLI restart, concurrency/count per binding, binding removal or reconfiguration, and closure of live sessions. The census explicitly identifies these missing answers (`state.yaml:419–430`). |
| `McpServerBinding → credential custody` | Three credential kinds stay separate. Shared generation, active generation and custody references exist; the auth draft explicitly calls their reuse a **candidate, not a decision** (`.engineering/planning/story/mcp-outbound-auth-lifecycle.md:37–55`). | **Keep UNMAPPED.** No independent MCP secret owner and no direct binding→custody field can be justified from these sources. | Select the binding→Connection mapping and reuse of existing acquisition/generation/custody/publication owners, or explicitly justify another owner; specify repair/revoke/retention effects. This is a prerequisite for complete outbound auth modeling. |
| `McpInboundSession → McpCaller` | Local stdio admits exactly the configured owner and acquires no inbound wire credential (`server semantics:45–65`). It supervises the connection through the existing shared Session, while `McpInboundSession` is a legacy-protocol noun (`server semantics:67–93`). | **Keep UNMAPPED globally; introduce no McpCaller entity for the single-owner slice.** Exactly one admitted local principal does not establish a persistent caller entity or its lifecycle. | If a multi-caller placement is selected, decide the existing owner of authenticated caller identity, session reference/cardinality and revocation coupling together with the caller-assignment decision. The accepted local contract explicitly retains this marker (`server semantics:122–126`). |
| `McpCaller → Connection` | Every downstream attempt selects one Connection; that does not decide which callers may select it. The local owner has no multi-caller assignment problem (`.engineering/planning/decision-blocker/mcp-caller-connection-assignment.md:19–24,44–55`). | **Keep UNMAPPED and the existing blocker open.** Do not choose per-caller allowlists, shared connections, caller ownership, or revoke cascades as implementation defaults. | Actual operator decision: caller identity/binding, assignment cardinality, ownership and revoke/outliving behavior. Existing blocker lines 68–77 explicitly reserve this decision rather than letting a contract author adopt a hosted identity dependency. |
| `McpServerBinding → supervised OS process` | This question concerns **outbound stdio**. Outbound HTTP and inbound stdio are not behind it; inbound's MCP client launches Connectors as its child (`client semantics:695–708`; `server semantics:36–43`). | **Keep UNMAPPED and the existing blocker open.** Mark this relation inapplicable to the selected HTTP slice; do not encode global cardinality zero. | Actual operator decision: spawn/own versus attach, one child per binding versus per session, pin/digest/restart policy and process lifetime (`.engineering/planning/decision-blocker/mcp-outbound-stdio-process-ownership.md`, “The relation nobody has decided”). |

The five design choices in rows 1–5 need an explicit authored decision/model source before their fields or cardinalities are added. They are not already answered by the lifecycle documents, and this audit does not manufacture answers. Nor do the sources make each one an additional operator-only permission gate. Rows 6–7 share the caller-identity/assignment boundary; row 8 is the separate process boundary.

## Minimal outbound HTTP design proposal — not accepted evidence

The following is a concrete proposed selection for root-owned ESS/contract review. It deliberately chooses among the open alternatives; none of these choices is claimed to follow from the accepted contracts. They are ordinary engineering design proposals, not five additional questions for the operator. The sixth non-filed relation, inbound-session→caller, remains with the existing caller decision; local single-owner work introduces no caller model.

| Open relation | Proposed cardinality and owner | Proposed lifecycle |
|---|---|---|
| Binding→configuration | Each outbound HTTP `McpServerBinding` references exactly **one** configured MCP adapter instance; each such instance selects exactly **one** remote endpoint/transport/revision at a time. `ServiceConfiguration` remains the configuration owner; the native binding is its MCP projection, not another configuration authority. | Configuration revision fences selection. Disable/removal closes the binding to new work and retires its live protocol state; already-dispatched effects retain their existing completion/uncertainty semantics. Endpoint or protocol reselection is an explicit configuration change, never discovery-driven. No automatic deletion of saved credentials or audit records. |
| Binding→Connection | One selected server binding can reference **zero or many** existing shared Connections, representing separately saved credential/profile identities under the same configured instance. Each such Connection already belongs to exactly one instance. Each invocation explicitly selects **one** Connection; the binding supplies no default-account fallback. Do not duplicate the generic Connection registry in an MCP-owned list. | Unconfigured/unconnected bindings have zero Connections. Connect/repair/revalidate/revoke use the existing Connection owner. Connection revocation prevents later admission and retires that Connection's live client state; it does not delete the configured server or sibling Connections. A configuration change requires current generic binding/admission checks; it never silently repoints an old credential to another endpoint. |
| Binding→custody | **No direct MCP custody ownership or independent secret record.** The binding reaches zero-or-many credentials only through its Connections; each selected Connection uses its existing zero-or-one active generation and zero-or-one active custody version. Generation history and superseded custody references retain their existing owners. | Credential acquisition, immutable capture, CAS publication, refresh coordination, identity-preserving repair and revoke fences remain generic-host responsibilities. Native outbound credential values carry only the admitted captured capability/handle for the selected use. A native session or cache disappearing does not delete the saved credential; generic retirement owns material cleanup. Keep inbound caller, outbound server and underlying provider credential kinds separate. |
| Binding→snapshot | A binding has **zero or many transient snapshot values**, partitioned by its exact configuration revision and selected Connection/revision/credential-generation tuple, with **at most one current value per tuple**. This is a bounded process-local cache, not a new persistent snapshot entity and not an authority relation. Apply descriptor visibility under the selected Connection; do not share authenticated discovery between credentials. | Replace, never append unbounded history; obey freshness hints and the absence-of-freshness rule. Discard on configuration/Connection/generation change, revocation, owner restart or invalidating peer notification. Rediscovery cannot alter configured selection or grant admission. This trades repeated discovery after restart for avoiding a new durable cache/recovery owner. |
| Outbound session→binding | Each legacy wire-session record references exactly **one** binding and one selected Connection/client generation in transient runtime state; a binding may have **zero or many** such records, at most one live legacy session per selected Connection/client generation. **Zero legacy sessions** for the stateless primary revision. No persisted wire-session recovery. | Legacy initialization/readiness/loss/close follow the accepted client lifecycle. An owner restart establishes a fresh session on a new admitted interaction; CLI exit alone need not terminate the still-running owner. Binding disable/reselection or selected Connection revocation retires the affected local session and attempts the selected bounded remote close; an unobserved effect remains unknown and is never replayed. Live sessions cannot continue dispatching against an obsolete binding/generation. |

These proposals reuse the generic cardinalities cited in the next section, but the *application to MCP*, multiplicity per binding, cache partition and transient session policy are new decisions. Record and review this five-row mapping as one cohesive outbound-HTTP design selection before changing fields, adding behaviors or closing markers. Exact cache ceilings and concurrency/close behavior must be named in that contract/model review, using existing operation limits; this audit does not fabricate new numeric limits. Preserve local single-owner admission without adding `McpCaller`, and preserve both pending operator decisions unchanged.

## Exact existing relations and lifecycles that can be reused

These are settled facts about **existing owners**, not proposed answers to the eight edges:

- **One advertised capability projects exactly one existing operation.** `McpAdvertisedCapability.operation_ref` is the scalar carrier; `state.yaml:319–364` explains the derivation and independent-root boundary. This is the census's already-stated edge, outside the eight. The draft projection story's citation to `AdapterSpecification owns many OperationDeclaration` names a different pair and cannot establish this cardinality or a deletion cascade. Use the native model's actual scalar-carrier source; separately specify removal from discovery without silently promising durable record deletion.
- **One Connection references one ServiceConfiguration.** `ess/domains/auth_bindings.yaml:115–116`. A Connection is administratively `Live` or `Revoked`, with revoke terminal; Live is not readiness (`:131–139`). This becomes relevant only after the MCP binding mapping is selected.
- **One CredentialGeneration references one Connection and one instance.** `ess/domains/credentials.yaml:40–50`. It is an immutable `Captured` identity record; it outlives material cleanup and does not itself own expiry/revocation/publication (`:51–61`).
- **A Connection has zero-or-one active generation and zero-or-one active custody version**, plus many superseded custody references. ESS spells scalar relations `cardinality: one`, but their Optional carriers make the active references zero-or-one (`ess/domains/auth_bindings.yaml:109–121,139`). No active custody without active generation; material-free access has neither (`:122–130`). Do not copy a misleading mandatory-one credential relation into MCP.
- **Inbound local transport supervision already uses shared Session and one set of Binding coordinates.** Its states are Offered, Establishing, Ready, Closing, Closed, Lost; establishment admits the owner, then accepts and readies the supervisor (`server semantics:67–93`). Data leases, renewal and terminal deadlines already apply (`:95–112`). The scalar `connection_ref` here is explicitly a supervision coordinate, not caller assignment (`:114–130`); shared ESS still defers the actual persisted Session→Connection join (`ess/domains/sessions.yaml:55–65,84–95`). Do not relabel shared Session as McpInboundSession or introduce a stub join.

## Smallest ESS work and contract dispatch order

1. **Start outbound invocation/results and single-owner inbound projection without any of the eight relation edits.** Their accepted prerequisites already permit live result/error mapping and single-owner admission. Keep transient values transient; maintain marker references and avoid sessionful language for the primary stateless revision. No new entity is necessary merely to write these contract lanes. The projection lane uses the already-stated operation edge, not a new caller relation.
2. **Before full outbound auth or runtime binding work, record one cohesive mapping decision for configuration, Connection and custody.** Its acceptance must explicitly name identities/cardinality, active credential ownership, repair/revoke behavior and removal/reconfiguration behavior. The auth story already states why prose alone cannot answer this. Preparing failure mappings and credential-separation scenarios can proceed, but cannot claim to have closed that model dependency.
3. **Then make only the selected model changes.** In `adapters/mcp/spec/ess/domains/state.yaml`, replace only the markers whose full answers were actually recorded. Add scalar/List/Optional carriers only when their multiplicity is justified. Native and shared ESS roots remain independent: do not import `connectors.auth_bindings.Connection` as a cross-root ESS target; use an explicitly specified adapter projection and its appropriately typed native carrier (`adapters/README.md:68–72`). Reuse shared lifecycle commands rather than inventing MCP-owned copies. If native transitions are required, specify their causing commands/outcomes; do not expand the current single-state noun census without behavior (`state.yaml:48–65`).
4. **Select snapshot and legacy-session lifetime only when a runtime/cache slice needs them.** These can remain marked while result/projection contracts are authored. Do not let an implementation cache or sibling library's current session handling make the product decision implicitly.
5. **Keep both filed blockers and the inbound caller-entity marker intact for the scoped slices.** Local stdio does not need a new durable caller entity; HTTP does not need a child-process mapping. This deferral is transport/placement scoped and does not complete multi-caller cloud isolation or outbound stdio.
6. **Coordinate the model census with any eventual selection.** `crates/connectors-build/tests/mcp_domain_model_census.rs:38–79` currently pins one stated edge, one absent edge, six unmapped edges and two filed edges. The adversary cases additionally reject disguised carriers on either endpoint and on values. Change only the newly sourced rows/expectations, retaining negative tests against unsupported edges; never remove guards merely to admit guessed fields. Update current normative references to changed markers while preserving historical review evidence. Validate the MCP root with the repository-pinned ESS and run the affected census/conformance checks in that future implementation task; neither was run here.

The other five draft follow-ups keep their existing sequence: auth after its model selection; mutation/replay after projection; composition after directional mappings; CLI/discovery after selected contracts; cloud profile only to the extent that it does not answer caller assignment. No new relation edit is justified merely by listing these follow-ups. In particular, a JSON-RPC request ID is not made a durable business key by the shared reservation→attempt relation, and snapshot retention does not decide durable invocation-record ownership.

**Actionable next step:** dispatch the two independent contract lanes now, with all eight markers preserved, and author the outbound HTTP configuration/Connection/custody mapping decision alongside them. Do not report any of those relations as already resolved; keep the existing caller/process operator questions open for their dependent slices.
