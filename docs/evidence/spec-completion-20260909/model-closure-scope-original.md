## Inventory and recommended bounded decisions

“Settled” below means directly supported by the cited text. Recommendations resolve authoring choices for a conservative first model; they are not already accepted contract rules. Every chosen change must be written in its owning contract before its ESS relation/command is called settled.

### 1. Connection and declared AuthProfile — required

**Settled.** Connection has a stable host-qualified ref, instance/profile, admitted owner/scope/actor, nullable established identity, fixed route, semantic revision and creation time. One instance/profile can have many Connections; at most one non-revoked Connection per established identity/instance/profile; null is not an identity key. Local revocation is terminal. Enablement and the seven viability observations are separate facts, not seven persistent lifecycle states. The active credential generation/version is absent for anonymous/mediated children and while no material has been published. Sources: [connection](../../contracts/auth/connection/v1alpha1/semantics.md), lines 32–49, 52–74, 80–98, 164–167; [design](../../docs/design.md), lines 1325–1326 and 1346–1358.

AuthProfile is an immutable reviewed adapter declaration, with id, purpose/subject/scheme, acquisition declaration, scope/evidence requirements and safe source references. A change is a specification revision requiring review of referencing Connections. Registration secrets are deployment configuration/custody, not profile fields. Sources: [profile](../../contracts/auth/profile/v1alpha1/semantics.md), lines 30–55, 89–106 and 155–162. Existing `ServiceConfiguration.instance_id` already supplies the running-instance reference; do not add a second Instance entity.

**Recommend.** Introduce a Connection administrative lifecycle `Live → Revoked`, with enablement and publication/readiness represented independently; creating a public pending record remains optional. Use references to ServiceConfiguration and AuthProfile, never deletion ownership over either. Qualify profile identity by adapter declaration plus profile id, and retain an explicit declaration revision reference. Keep AuthProfile a declared immutable record; no deployment/credential lifecycle on it. Profile declarations can be referenced by many Connections and operation requirements. A changed owner/parent/target creates a new Connection. Keep terminal Connection identity/fence records without automatic expiry in the first binding; bounded storage refuses new work instead of recycling them.

**Still a real decision:** final profile identity qualification and terminal-record compaction policy; whether an unactivated Connection is publicly allocated. The recommendation chooses no public record before initial managed publication, but permits configured pending records under existing admission. No tenant/account/assignment entity or cross-tenant cardinality is needed for this local slice. Lifecycle labels and these reference kinds must be ratified in prose before ESS.

### 2. Acquisition and immutable custody version — required for the selected managed-auth semantics

**Settled.** An Acquisition has its own opaque id, one logical coordinator, admitted origin/owner scope, selected profile/registration, expiry and one-use correlation; optional repair target; a completed result yields one Connection. Several acquisitions may target one Connection, but stale concurrent completion cannot win publication. Static configuration creates no Acquisition. Credential exchange/correlation consumption precedes durable custody and acknowledged guarded metadata publication; unknown exchange cannot be resent. Sources: [acquisition](../../contracts/auth/acquisition/v1alpha1/semantics.md), lines 30–50, 73–91, 186–193; [design](../../docs/design.md), lines 1327 and 1346–1352.

Custody identity is `(scope, version)`; each immutable version contains one coherent bounded CredentialSet. `write_new`, `read` and `delete` have explicit uncertain outcomes. Active/superseded are Connection reference facts, not custody states. Reclamation requires no valid use and declared retention (default 24 hours); default eight retained versions includes active. Source: [custody](../../contracts/auth/custody/v1alpha1/semantics.md), lines 32–54, 58–77 and 110–113.

**Recommend.** Acquisition `Pending → Completed | Failed | Expired`, preserving Expired internally and projecting it as the existing public failed/expired reason; failure never erases the established repair target. Reference profile/optional repair Connection, with an optional completion reference constrained to exactly one on Completed. Keep protected correlation as a private owner value, not a public callback credential or new tenant entity. Retain the consumed/terminal correlation fence through its validity window; expiry makes a handle permanently unusable, not reusable. The exact callback codec remains a separate protected-ingress binding obligation.

Model one CustodyVersion, with embedded CredentialSet metadata/private material handle, not separate access-token/refresh-token entities. Version ownership belongs to the scoped custody authority; Connection and CredentialGeneration reference versions without owning/deleting them. Keep active and superseded references on the auth metadata owner. Recommend no automatic terminal ledger deletion and no deletion of consumed-refresh facts. For superseded material, define retention from acknowledged supersession, with deletion only after both that interval and all valid-use obligations end; uncommitted orphan cleanup must separately prove no possible publication/recovery use. Unknown cleanup cannot imply absent material. The capacity rule is refusal, never eviction of still-required material.

**Still real decisions:** explicit expiry/public-result mapping, correlation/tombstone retirement proof, custody orphan retention origin, and which private command establishes no remaining valid use. These need a declared first-binding rule, not a guessed ESS owns edge. No new grant types, OAuth profiles or callback-host routing product are needed.

### 3. Execution audit — required by the selected service binding

**Settled.** Each hop owns a durable acknowledged admission anchor before dispatch and a separately appended final observation linked to it. Public `{instance, audit_ref}` identifies acknowledged audit; complete/incomplete describes recorded observation, not business certainty. Final append can fail independently and cannot trigger redispatch. Early records omit unverified caller/operation coordinates. Attempt evidence outlives replay-cache retirement; approval compaction cannot delete linked attempt/audit evidence. Sources: [service compatibility §5](../../contracts/service/compatibility.md#5-extended-responses-audit-and-mutation-observation), lines 76–82; [operations](../../contracts/operations/v1alpha1/semantics.md), lines 160, 185–187; [delegation](../../contracts/service/delegation.md), line 152; [design](../../docs/design.md), lines 1335, 1350 and 1358.

**Recommend.** One AuditRecord aggregate keyed by a host-qualified safe anchor, containing the immutable admitted facts and an append-only sequence of safe outcome observations. Its authoritative lifecycle distinguishes admission recorded from final observation recorded; public unavailable is absence of an acknowledged anchor, not a persisted empty audit entity. Each observation has an owner-allocated stable append identity for acknowledgement/recovery; repeat observation of that identity adds no duplicate append. Optional attempt correlation is a reference, not ownership: reads also require audit and gateway/leaf have distinct records. No secret, native target, input body or protected correlation fields.

**Still real decisions:** permit one logical final observation with idempotent acknowledgement recovery, or explicitly define multiple revisions; safe per-record fields/bounds; retention and deletion. Recommend one logical final observation for this first binding, no automatic audit expiry, bounded capacity refusing new admitted work, and no hard delete/compaction that drops facts required by another owner's safety predicate. This closes a conservative model without inventing an audit exporter, query service, cross-store transaction or retention duration. A shorter/product retention policy is later explicit work.

### 4. Discovery collection/observation and mediated binding — required for Kubernetes discovery; mediation remains separately selected

**Settled.** Collection equality includes instance, source Connection, declaration/profile/revision, configured provider authority, finite membership, interpretation and disclosure scope. One host metadata authority publishes a complete classified view plus private binding index atomically; an attempt id, predecessor and current fences govern publication/unknown acknowledgement. Only one current view per scope is served. Observation ids identify qualified source/incarnation; positive withdrawal is terminal; changed target or lost continuity needs a new id. A physical resource may have multiple observations, an observation multiple children. Sources: [resources](../../contracts/discovery/resources/v1alpha1/semantics.md), lines 97–101, 117–137 and 213–216.

Retention is already selected: 500 rows, 256 scopes, 600-second history, 300-second cursor/evidence ceiling; expired view/cursors retire atomically and children cannot pin unbounded history. Source: same document, lines 172–179. View classification is immutable; current authorization is rechecked separately.

**Recommend.** A source-referencing DiscoveryCollection owns its bounded private observation records and current snapshot value. Explicitly qualify observation incarnation by collection scope epoch: the same physical resource can produce independent observations across differently admitted scopes, and withdrawal in one cannot terminalize another. Do not introduce a physical provider Resource entity. Scope retirement retires its view and bounded rows; surviving child coordinates cannot prevent cleanup or authorize later use. Preserve non-reuse through a fresh epoch when continuity is lost. The exact association of incarnation with scope is a real model decision, not fully declared by the current identity prose.

The mediated binding is fixed configuration **on one child Connection**, with parent, original observation incarnation, profile/target and separately changing private route evidence revision; child has zero or one such binding and parent cannot itself be mediated. Use an embedded route value keyed by that existing child ref, not another arbitrary route id/lifecycle. A stored fixed observation coordinate remains safe historical data when its current row is absent; a mandatory live foreign-key relation must not pin discovery history. Current observation resolution is optional and absence refuses routing. Source: [mediated route](../../contracts/discovery/mediated_route/v1alpha1/semantics.md), lines 42–45, 65–80 and 82. Revalidation is same-target CAS under the shared binding metadata authority; target/owner changes require a new child. The gateway `idempotency.RouteBinding` remains a different value.

**Still real decisions:** explicitly select collection ownership/scope qualification and non-pinning route association above; define retire/publication command outcomes. No independently durable ScanAttempt is implied by transient collection work: only the acknowledgement/recovery identity required by the published metadata owner must persist.

### 5. Composition — configuration/value closure, not a required durable entity

The authored executable selects installed implementations, creates independent logical instances, injects private ports, owns process supervision and aggregate limits. Discovery does not install anything. Sources: [composition](../../contracts/discovery/composition.md), lines 5, 23–41; [design](../../docs/design.md), line 1341. Existing CompositionFacts is a value.

**Recommend.** Type an immutable configured composition declaration containing instance references, installed binding/revision references and aggregate limit values only where needed by discovery/route admission. Preserve process/live-port predicates as explicit binding obligations. Do not invent Created/Running/Stopped database entities or delete ownership over Connection/ServiceConfiguration. Dynamic installation/restart/provisioning lifecycle is deferred.

### 6. Source, Bundle, CatalogIndex and Curation — split artifact declarations from optional catalog service

**Settled.** Source proposes url+revision identity and origin/kind/hash/license/transforms, reusable across many AdapterSpecifications. Bundle identity is its digest, with exact manifest/toolchain/source hashes and files, realizing one specification. Curation is an embedded operation value, not an entity. Index identity is its digest and one generation is served at a time. Sources: [catalog](../../contracts/catalog/v1alpha1/semantics.md), lines 78–88, 129–147 and 195–200.

**Recommend now.** Type immutable generic Source/Bundle declaration records and Curation values needed to describe the existing three adapters' artifacts. Source feeds/specification references are many-to-many; a Bundle references one specification plus its exact revision/digest. Preserve existing AdapterSpecification identity; do not silently make adapter_id identify every historical revision or rewrite the accepted strict adapter reader. Curation's semantic source fields may be modeled while reader/schema adoption remains explicitly proposed.

**Actual optional catalog decisions.** The table's proposed `CatalogIndex owns Bundle` and bundle `generated → indexed → superseded` do not say what happens when the same immutable digest is reused by two generations/consumers. Recommend index-owned membership values **referencing** independently retained immutable bundles; index replacement retires a publication selection, not the shared bytes. This revises the proposed ownership and must be made explicit. Catalog publication authority, tenancy and delete/retention/capacity policy remain UNMAPPED; no selected service protocol requires their implementation for Kubernetes/GitLab/SQL. Keep CatalogIndex/publishing lifecycle deferred and unadvertised, or commission that separate optional specification before claiming catalog service completion. Do not place a native CatalogIndex domain in shared ESS: any later catalog-specific model lives in `adapters/catalog/spec/ess/` and respects independent root boundaries.
