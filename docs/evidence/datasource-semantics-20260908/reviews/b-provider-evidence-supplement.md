# Common-provider evidence follow-up

This is supplemental source analysis after the immutable initial report, not another review round or a change of verdict. Initial verdict remains needs-revision with LD-B-01–08; no new finding is added. Eight common source files were copied and hash-checked before inspection; exact URLs and bytes are in source-hashes.json. No network or provider invocation was performed by this reviewer.

- Loki v3.7.0 at commit 3361de24b692875d77bd7433cd6baa7c68dc0ef9 specifies an inclusive start and exclusive end, with a line limit applying to stream responses; the same range endpoint accepts metrics (snapshot/loki-v3.7.0-http-api.md:464–475). This supports LD-B-02/03 and makes a selected [start,end) mapping concrete.
- The pinned LogCLI implementation terminates with an error if the retained timestamp overlap fills its batch (snapshot/loki-v3.7.0-logcli-query.go:177–182); its next forward query keeps the tie timestamp and backward query raises the exclusive end by 1 ns (:185–200). This supports LD-B-01, not unlimited safe continuation or an occurrence-identity guarantee.
- Current Confluence v2 has a GET /pages collection with independently described id and space-id filters and a body-format selector (snapshot/confluence-v2.openapi.json, /paths/~1pages/get/parameters); GET /pages/{id} has no space-id filter (/paths/~1pages~1{id}/get/parameters). A fixed conjunction can retain by-ID native body capability instead of limiting this story to metadata, subject to exact response/space/body checks and a selected provider-observation guarantee. The current v1 snapshot has /wiki/rest/api/content/search but does not contain the old content/{id} GET; historical pin and current surface must be distinguished. These facts support an explicit source binding for LD-B-05/06; they do not prove all preexisting v1 endpoint behavior migrated unchanged.
- Jira v2 GET issue describes fallback resolution of moved or case-variant issue keys and returns the resolved key without an HTTP redirect (snapshot/jira.openapi.json, /paths/~1rest~1api~12~1issue~1{issueIdOrKey}/get/description). A key-prefix check or redirect rejection therefore cannot establish configured project membership. Current parameters support selected fields, and the default GET includes all fields; a minimal membership response and native full-body representation can be distinct bounded bindings.
- Enhanced Jira GET /rest/api/2/search/jql supports a bounded JQL query, fields=*all, and reconcileIssues; the parameter admits up to 50 exact issue IDs kept consistent through pagination (same snapshot, /paths/~1rest~1api~12~1search~1jql/get). The separate official search-and-reconcile article explains that ordinary search can lag recent updates, confines the stronger consistency to specified IDs, and states reconciled results still satisfy JQL (snapshot/jira-search-reconcile.html, “More about reconciliation” and “Using Rest API”). This gives a plausible scope-constrained full-document read rather than a metadata-only substitute, but it does not confer a cross-request immutable snapshot, durable membership authority, or a blanket cache lease.

The root's revised selection must still settle exact IDs versus aliases, configured key-to-provider-ID mapping, fixed authority/destination, limits and malformed/missing response behavior, content/membership observation boundaries, and current-admission cache reuse. No baseline finding is closed merely because the upstream has an applicable endpoint. Runtime conformance remains outside this review.
