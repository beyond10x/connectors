# GitLab

Eleven bounded reads and persistent local credentials in source release v0.2.0.

[Follow a request from your laptop to GitLab](/introduction/examples) to see federation, the separate authentication boundaries and the issue response.

## Current capabilities

Use `project.get` to inspect an allowed project, `issues.list` for a bounded issue page, and `file.get` for repository content.

For CI, `pipelines.list` selects one exact full commit SHA; `pipeline.get` observes
the selected pipeline's native status. `pipeline.jobs` pages its current job
attempts, `job.get` verifies a job's pipeline and SHA, and `job.trace` returns a
bounded UTF-8 prefix with explicit completeness. A successful pipeline for another
SHA cannot satisfy the selection. Read the [CI contract](/adapters/gitlab/contracts/ci)
for input shapes and limits. Dedicated GitLab sandbox acceptance remains open.

`merge_request.get` reads an MR by project-local IID. `merge_requests.list` traverses
a fixed inclusive update window with bounded pages and explicit completeness.
Unknown statuses and missing heads remain observations; they do not validate a
merge. Read the [MR contract](/adapters/gitlab/contracts/merge-requests) for window,
cursor and projection rules. Mutable pages are not a snapshot or lossless feed;
the consumer owns its checkpoint.

`merge_request.validate` checks an exact requested MR source SHA and selected
successful head pipeline, together with opened, non-draft and mergeable status.
The result contains `checks_passed`, ordered `blockers` and
`merge_performed: false`. A negative validation is a successful read: inspect
`checks_passed` even when the CLI exits successfully. A passing observation
does not reserve the head or authorize a later write. See the
[validation contract](/adapters/gitlab/contracts/merge-validation).
The development checkout also implements `merge_request.merge` through explicitly
selected `connectors-local/2` and `connectors-private/2`, with a saved PAT granting
`api`, current local approval policy, signing keys and an authenticated clock.
Prepare and issue a proof for the exact input, then pass its owner-private path
as `--approval-file` and an optional `--idempotency-key` to `operations invoke`.
Fresh preflight precedes one source-SHA-guarded PUT. Results carry mutation and
audit observations; an unknown outcome never triggers another PUT, and an exact
retained key can observe the original attempt after restart. This development
feature is outside v0.2.0; its wider failure and sandbox acceptance remain open.
Create/update workflows remain unfinished.

## Use saved credentials

The local CLI requires Linux x86_64 and the qualified GNOME Keyring Secret Service
binding described in the source guide `docs/local-secret-service.md`: the pinned
Arch Linux GNOME Keyring 50.0 daemon on ext4, with an already-unlocked encrypted
login collection. Other daemon builds and filesystems require qualification.
SQLite stores connection metadata; credentials stay in the keyring.
Existing installed configuration and credentials are not automatically imported.
Build the optimized CLI and adapter so supervised startup fits its bounded budget:

```sh
CARGO_BUILD_JOBS=2 cargo build --release --locked -p connectors -p connectors-gitlab
target/release/connectors --output json setup init
target/release/connectors --output json setup check
```

Create a private native configuration file with your endpoint and permitted projects:

```json
{
  "format": "connectors-gitlab-local/1",
  "instance": "gitlab-local",
  "api_base": "https://gitlab.example/api/v4",
  "allowed_projects": ["group/project"]
}
```

Keep it owner-only in a directory without symlinks. Read the native bootstrap and
hash the executable:

```sh
target/release/connectors-gitlab --local-config /absolute/path/gitlab.json --print-local-bootstrap
sha256sum target/release/connectors-gitlab
```

Add this entry to the TOML configuration created by setup, substituting the exact
bootstrap revision, executable hash and absolute paths:

```toml
[adapters.forge]
instance_id = "gitlab-local"
adapter_id = "gitlab"
configuration_revision = "REPLACE_FROM_BOOTSTRAP"
protocol = "v1alpha1"
startup = "on-demand"
restart = "never"

[adapters.forge.permissions]
profiles = ["gitlab.pat"]
operations = ["project.get", "issues.list", "file.get", "pipelines.list", "pipeline.get", "pipeline.jobs", "job.get", "job.trace", "merge_request.get", "merge_requests.list", "merge_request.validate"]

[adapters.forge.executable]
path = "/absolute/path/connectors-gitlab"
sha256 = "REPLACE_WITH_EXECUTABLE_SHA256"
args = ["--local-config", "/absolute/path/gitlab.json"]
```

Connect using the hidden PAT prompt, then describe the operation:

```sh
target/release/connectors --output json connections connect --adapter forge --profile gitlab.pat --credential-prompt
target/release/connectors --output json operations describe --adapter forge --operation project.get
```

Use the returned connection reference and the operation's current schema and
descriptor revision:

```sh
target/release/connectors --output json operations invoke --adapter forge --connection CONNECTION --operation project.get --schema SCHEMA --revision REVISION --input-json '{"project":"group/project"}'
```

Later invocations reuse the saved credential, including after owner restart.
Validation evidence lasts at most 60 seconds. When it expires, explicitly
revalidate the saved credential using the current connection revision:

```sh
target/release/connectors --output json connections revalidate --adapter forge --connection CONNECTION --expected-revision CONNECTION_REVISION
```

Revalidation requires no credential re-entry. Invalid or missing credentials need
`connections repair`; `connections revoke` is terminal local revocation and does
not revoke the PAT at GitLab. Listing, status and cached descriptions start nothing.
Protected file and stdin entry, exact stop selectors, CI/MR input shapes and
keyring qualification are detailed in `docs/local-gitlab-cli.md` in this source release.

## Access and limits

Configure the GitLab endpoint and an explicit project allowlist. Public reads can use no provider credential; private reads use a separately bound token. Caller authentication to the adapter service is a different boundary.

File content follows its declared representation and byte limits. Read the native contract for pagination, provenance and refusal behavior.

## Run a standalone service

The existing explicit service interface remains available. Build the workspace,
choose this adapter's example configuration and bind private credentials separately
from operation input. The [getting-started guide](/introduction/getting-started)
explains that workflow.
