## Outcome

An `invalid_input` or `cli_parse` refusal names the argument or input field it refused, so a caller
can correct its call without reading the source.

## Today

Reported by a downstream consumer on connectors 0.50.0, 2026-10-14: `invalid_input` and
`cli_parse` refusals name no field, across all 48 operations it uses. The CLI parse refusal is
generated by ESS's CLI binding, which does not name the declared argument today; that part is
upstream (the ESS story for parse refusals that name their declared arguments).

## Change

Spec first: the refusal detail gains a `field` (the CLI argument, or the JSON pointer of the input
member) wherever Connectors decides the refusal: operation input validation in the host and the
catalog provider, and the CLI's own checks. The parse refusal follows when the ESS binding names
its argument; until then the refusal says the argument is unknown, and this story records the
upstream dependency.

## Acceptance

- Tests: an invalid operation input names its JSON pointer; an invalid CLI argument that Connectors
  checks names the argument.
- The upstream dependency is recorded as a relation, not a workaround.

## Scope

Primary: ess/domains/cli.yaml connectors.cli.Failure (+field), regenerated CLI contract, apps/connectors/src/local.rs and local/*.rs, connectors-host owner.rs validate_document, connectors-sdk validate (keep instance path), catalog lib.rs/feed.rs/local.rs; inferred private channel Reply::Failed in runtime.rs/process.rs, connectors-core Error, private-adapter.md. Wide: collides with every cli.yaml/local.rs/runtime.rs unit. Safety: field from declared schema, never caller text (additionalProperties).
