## Defect

beyond10x/connectors#105: `connectors --output json operations describe` answers
`result.operation.input_schema` and `output_schema` as strings holding JSON, and
`operations invoke` answers the provider result as JSON text in `result.result`. Callers parse
twice; the beyond10x/examples triage demo had to handle both forms (`zendesk-triage/src/zendesk.rs`
`invoked_answer`).

## Acceptance

Decided 2026-10-06: the CLI contract is `v1alpha1`, so the answers change in place, recorded as a
breaking change in `CHANGELOG.md` `### Changed`, rather than under a new output version.

- `connectors.cli.OperationDescription` declares `input_schema` and `output_schema`, and
  `connectors.cli.OperationInvokeResult` declares `result`, as JSON values, not `String`
  (`ess/domains/cli.yaml:419-427`, `:659-665`); `contracts/cli/v1alpha1/semantics.md` and
  `fixtures/values.json` state the JSON form.
- `operations describe`, `adapters describe` and the legacy describe (which share
  `OperationDescription`) return the schemas as JSON objects, and `operations invoke` returns the
  provider result as a JSON value; the schema digest stays the identity.
- A test per answer pins the JSON form, and the tests that read the text form today
  (`crates/connectors-conformance/tests/cli_surface.rs:592-607`, the catalog, Kubernetes and SQL
  `local_runtime` journeys) read the new form.

Not in this story: the beyond10x/examples triage demo, which already reads both forms
(`zendesk-triage/src/zendesk.rs` `invoked_answer`); `ServiceDescriptor.configuration_schema`,
which has the same text form but is not in #105.
